# Ozagia integration analysis against the Ozma Protocol

Reviewed 2026-11-17 against the `ozma-ai/research` checkout (`ozma-ai` HEAD `33a39c8`, with unrelated uncommitted backend changes); the material has since been [preserved locally](research/ozma_protocol/README.md) as Ozagia's design basis. The primary references are the draft [Ozma Protocol v5.16](research/ozma_protocol/upstream/docs/protocol.md), [map format](research/ozma_protocol/upstream/docs/maps.md), [shim requirements](research/ozma_protocol/upstream/docs/shim.md), [foundation](research/ozma_protocol/upstream/docs/foundation.md), and the later [whole-surface partition design](research/ozma_protocol/upstream/docs/protocol-partition.md). The review compares the specification and selected code with [Ozagia's capability integration analysis](ozagia_capability_integration_analysis.md); it is not a conformance certification. The separate [L4 design](research/ozma_protocol/upstream/docs/l4_plan.md) calls its proof of concept pending and should not be treated as a deployed transport.

## Assessment

The analysis points in the same direction as the protocol, but **it underweights the model–runtime boundary and the map lifecycle**. It describes how Ozagia's services and evidence could form a graph; the protocol additionally defines how appropriately scoped, typed information is assembled, negotiated, exchanged, checked and applied around a model. A graph of capabilities and work is valuable, but it is not itself the model protocol, a semantic map implementation, or proof that a model can consume a particular encoding.

A better architecture is complementary:

1. **Ozagia** owns or exposes workspace facts, tools, bounded tasks, local execution, evidence and policy enforcement.
2. **The Ozma protocol and shim**, where actually deployed, describe the model-facing schema, adaptation, parsing, validation and fallback at the token boundary.
3. **Ocelot** is the separate cognitive engine; it may supply cognitive operations and scientific reasoning to a workflow through an explicit integration.
4. **The model** performs the inference supported by its actual capabilities; the host retains responsibility for state, authority and verification.

This is a proposed division of responsibility, not an assertion that the products already form an integrated runtime. Ozagia's [existing Ozma context provider](ozma_integration.md) is a versioned, read-only Python context boundary. Its documentation describes an opt-in Ozma backend assembler integration. It is not evidence that Ozagia implements the Ozma protocol's handshake, map engine, model-facing grammar or all shim requirements. Likewise, Ozagia's JSON-line daemon protocol and MCP tools are different interfaces, not implementations of the Ozma model language merely because they are called protocols.

## Comparison

| Protocol concept | Ozagia's existing or proposed analogue | Review finding |
| --- | --- | --- |
| **Maps:** typed, scoped, versioned, content-addressed, composable schemas and instances | Typed graph nodes/edges, snapshots, task specs, research records, model graph, view models and evidence packets | The analysis calls for stable identity and provenance but does not specify a map schema, scope, fingerprint, lifecycle, composition or canonical serialization. Add an adapter boundary rather than relabeling every Ozagia structure as an Ozma map. |
| **Model surface versus backend** | Ozagia daemon, MCP/CLI, hooks and native harness supply context and tools | Specify which facts remain host-side and which compact, bounded representation crosses the model boundary. Persist state and enforce permissions in the host; use model-facing schemas only where the model needs to participate. |
| **L0/L1/L2 and per-capability fallback** | Existing harness integrations and advisory model graph | The model graph is not the protocol capability registry. Negotiate supported schemas and fall back per capability; a model name, size or estimated profile is not proof of protocol competence. Preserve usable plain-tool paths for stock models. |
| **Registry, fingerprints, probe/ack** | Typed settings and model registry exist | Define ownership and a versioned registry for actual protocol support and implementations. A claimed or parsed acknowledgement must not grant permissions, override policy, or establish semantic competence. Verify actual implementation rather than assuming the draft handshake is secure or supported. |
| **GRAPH, OUTLINE, INTERACT, EDIT** | Repo graph/search/impact, graph-addressed operations and transactional edits | Map Ozagia node keys and snapshot provenance to protocol references with explicit scope, version, stale-reference handling and lossless conversion. Route edits through Ozagia's existing preview/hash/transaction policy; never trust a model-emitted edit just because it parses. |
| **WORK-UNIT, PLAN, TASK and DISPATCH** | Goals, bounded tasks, background jobs, session state and task classes | These are related but not identical types. Map lifecycle, budgets, cancellation, ownership, run status and evidence explicitly. Current bounded runner does not itself call a model; avoid claiming that protocol dispatch is already implemented by it. |
| **MEMORY and session cache** | Session graph, working set, repeat-read ledger, research records and content hashes | Distinguish durable evidence from conversation memory and token-saving caches. Define scope, authorization, invalidation on source changes and compaction, retention, and behavior on cache miss. Do not equate a read ledger or graph snapshot with the protocol MEMORY lifecycle. |
| **CLAIM / FORMAL-CLAIM and verification continuum** | Goal criteria, tests, review findings, research claim/evidence records, Lean export and optional Ocelot integration | Model assertions, static observations, test outcomes, independent review and machine-checked proofs have different assurance. Record verifier, inputs, result and assumptions; a valid proof is conditional on premises and a passed test only covers its actual run. |
| **ROUTING-CONTEXT and capability probing** | Model catalog, toolchain readiness and advisory matching | The analysis needs a model-facing, policy-filtered view of what is available, enabled, trusted and reachable—not a dump of every model/tool. Ozagia's existing matching remains advisory, not automatic protocol routing. |
| **CONTROL / COMMUNICATE and IFC** | Source-attributed context, permissions, bounded tasks and research ingestion | Origin and trust labels must survive projection and enforce authorization at the host. The draft's claim that channel semantics eliminate prompt injection is a design claim, not a demonstrated guarantee for arbitrary models; use isolation, validation and adversarial tests. Authorized user requests also need an explicit policy path, not a blanket classification that makes them ineffective. |
| **TASK / ambient long-running work** | Daemon background jobs, wait and working-set briefs | Compare elastic await, wake conditions, output visibility, budgets and session reattachment individually. Existing jobs do not by themselves establish full TASK protocol compliance. |
| **WIRE / encoding** | Token budgets, context hints, repeat-read notes and measurements | Treat compression as an optional, negotiated transport layer with a correct fallback. Measure actual tokenization, parse reliability, model success and end-to-end latency; do not assume shorter text or a new codec improves task outcomes. |

The protocol's `FEDERATED` datatype concerns federated-learning annotations; Ozagia's repository federation is a different concept. Shared terminology does not establish interoperability.

## Changes to the proposed internal graph

The internal graph should remain a **logical, provenance-preserving view** of Ozagia's capabilities and the work it performs. Add the following protocol-facing concepts to the integration design:

- **Schema and map records:** identity, schema version and fingerprint, scope, owner, source, sensitivity, lifecycle and supported adapters. Separate a schema from a populated instance and its rendered representation.
- **Capabilities as contracts:** distinguish an Ozagia service implementation, its availability and permissions, and the model/shim's negotiated ability to understand a representation. Record supported versions, negotiated subset and fallback—not a single model capability score.
- **A projection boundary:** define a task-specific view that maps graph facts to a bounded model-facing context or protocol map, with explicit omissions, source/revision, freshness and trust labels. Project only what is required; do not transmit the whole internal graph.
- **A reverse boundary:** parse model output against the applicable negotiated schema, resolve references against their scoped snapshot, validate types and semantics, then pass actions to existing authorization and transaction machinery. A parseable output is not an authorized or correct action.
- **Trace and verification edges:** connect each projected map and model invocation to inputs, schema, selected capability/fallback, output validation, actions and independent check results. Record partial, stale, unknown and rejected states; do not expose private reasoning as a prerequisite for useful audit.
- **External state versus model context:** the host owns durable state, secrets, credentials, policy and resource management. The model receives appropriate references and observations, not unrestricted state or authority.

## Practical integration path

1. **Contract inventory and ownership.** Catalogue the real Ozagia services and the actual Ozma shim implementation and versions. Name which process owns maps, caches, capability negotiation, execution and audit. Test the existing opt-in context provider end to end before changing the wire.
2. **One read-only vertical slice.** Project a small task-scoped repository graph/outline into one explicitly versioned representation, carrying qualified keys, source hashes, freshness and truncation. Provide the existing plain-context fallback. Compare against existing Ozagia context without claiming protocol conformance from similar field names.
3. **One validated return path.** In an isolated fixture, parse one supported output type and translate it to an Ozagia preview; check identity, stale base, permissions and transaction semantics. Only an explicitly authorized operation may apply it. Reject unsupported versions and malformed or ambiguous data safely.
4. **Work and evidence integration.** Map goal/task/check records to compatible work-unit and claim concepts, documenting fields that have no equivalent. Preserve actual verification level and do not make LLM-generated rationales a source of truth.
5. **Capability negotiation and caching.** Add a per-model/per-session capability record, schema fingerprint handling, cache invalidation and per-capability fallback only after a real shim boundary is selected. Treat model swaps, changing source files and compaction as explicit invalidation events. Keep authentication and authorization independent of generated text.
6. **Scientific/Ocelot slice.** Establish an explicit adapter for claim, assumption, derivation and verification evidence. Report whether a result is recorded, checked by a particular executable/verifier, or merely asserted, including premises and unsupported cases.

## Evaluation and open issues

Compare the same model, task, repository revision, tool access and acceptance tests across: plain agent; Ozagia context alone; Ozma shim/protocol alone; and both together. Also compare a carefully prepared plain-context baseline and multiple model tiers. Measure task success, parse and round-trip failures, rejection and fallback rates, source staleness, unauthorized-action attempts blocked at the host, prefill/decode and tool wait time, cold/warm setup, wall-clock, cost, tokens and operator work. Include malformed, adversarial, stale-reference and capability-mismatch cases. Test lossless serialization and edit transaction behavior independently of model quality. Use repeated runs and separate offline fixture validation from live model evaluations; Ozagia's live-eval approval gates still apply.

The draft foundation's strong claim that failures are predominantly context bugs, and the partition design's claims about native-model efficiency, are hypotheses or design positions to test—not established general results. The protocol specification also uses language that treats the COMMUNICATE boundary as eliminating prompt injection; a label or instruction to a probabilistic model does not itself prove isolation. Similarly, a model-emitted acknowledgement and a short hash are not sufficient evidence of model identity, authorization, or capability. These distinctions protect the shared goal: build dependable outcomes from explicit boundaries and evidence rather than assuming that any single representation or model behavior guarantees them.
