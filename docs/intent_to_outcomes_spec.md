# Ozagia intent-to-outcome requirements and specification

Draft for review, 2026-11-27. This specifies product behavior and logical interfaces. It makes no commitment to a transport, workflow engine, or UI framework.

## Product model

Ozagia is a scaffold that lets people and their chosen models work as a team of experts. Open Ozagia and state an intent, or invoke the same capabilities through an agentic harness, MCP, CLI or library. People can also run individual steps manually. A single operator, an existing team and a distributed group all use the same concepts. Ozagia supplies expertise as versioned graph content that equips a general-purpose model with domain knowledge, procedures, tools and independent checks. A specialist model is one possible contributor. A single model can use several kinds of expertise within one run. Larger deployments can delegate to multiple specialists.

Agents are interchangeable workers. Each assignment serves a specific outcome and records the task, skills and expertise versions, execution window, runtime resources, and inference provider and model when used. Continuity lives in the work, evidence and checkpoints. A compatible replacement can resume from that record under the current policy. The default interface emphasizes assignments and outcomes. Users may opt into names or avatars as presentation preferences. These labels carry no authority and do not affect scheduling.

The same outcome model applies to software, research, physical work and mixed efforts. Domain adapters supply observations, tools and verification methods. For example, a fabrication effort can link drawings, software revisions, measurements and a technician’s inspection. Ozagia can prepare instructions or coordinate a handoff. When the outcome depends on a physical observation or action, completion requires evidence from the responsible person or supported device.

People bring Ozagia an intent in ordinary language. Ozagia grounds it in the available conversation, repositories, artifacts and decisions, selects a proportionate course of action, and returns an outcome with evidence. A question can end with an answer. A standalone request can produce artifacts and survive a restart without ever belonging to a project. A project represents an enduring body of work with its own purpose, context and history. A single request inside a project can still end in one exchange.

Ozagia may propose a project or quietly create a private working grouping, then surface it when continuity or visibility would help. Tasks, attempts, worker assignments and queues are available on inspection. The default experience emphasizes outcomes, progress, changed assumptions and decisions requiring attention.

Human attention is the primary scarce resource Ozagia is designed to protect. Ask for input when it can materially change the outcome, resolve consequential uncertainty or satisfy a required decision. Surface information when it changes the user's understanding or gives them a useful action. Keep the underlying work and evidence available to inspect at any time.

Ozagia provides configurable identity, permission and approval boundaries. Operators decide where to enable them and can explicitly allow unauthenticated or shared-identity use for selected operations. Hosts enforce the resulting policy, including any organization or external provider requirements that apply to that deployment.

Projects can overlap. A supplier, instrument, dataset, repository or decision may be relevant to several projects, standalone requests and teams. Use typed links with provenance and independent access checks. Relate conflicting claims and competing plans explicitly. A shared relationship can inform impact analysis or prompt an intervention without expanding anyone’s access or silently coupling execution.

## Logical contracts

- **Context and expertise** use typed entity references and relationships carrying provenance, applicability and freshness. Capability records describe input and output types, applicable domains, prerequisites, execution location, effects, cost and verification options. Selection can combine human expertise, deterministic tools and models within a shared budget.

- **Intent** holds a stable ID, principal, conversation reference, requested outcome, context references, optional primary project for navigation, success criteria, interpretation and version. Record observations separately from interpretations. User steering creates a new version. Workers carry the version they accepted.
- **Project** holds an ID, purpose, owner, visibility, state, related work and evidence for each inferred association. Initial states are provisional and surfaced, with archive available from either. A provisional association is inspectable and reversible. Each linked artifact retains its own access boundary.
- **Project links** associate the same durable intent with zero or more projects. The optional primary project is a navigation preference. Linking and unlinking leave ownership, execution and history intact. Access to each link and its target is evaluated separately, including in summaries. If the primary link is removed, clear the preference.
- **Project backend** maps Ozagia project IDs to backend references and advertises read, write, watch and history support. Ozagia owns its cross-project links and intent lifecycle. Each adapter declares the authoritative system for mapped fields, uses revision preconditions for writes, reports stale or conflicting records, and checks effective permissions before reading or writing. On conflict, preserve both revisions for reconciliation. If the backend cannot enforce a required precondition, expose conditional writes as unsupported. Domain execution adapters separately describe effect targets and evidence baselines.
- **Work and attempt** represent a bounded unit and one execution of it. A work item points to its intent version and criteria. An attempt adds work context and baseline, worker, capability, expertise and policy versions, limits, lease generation, status and evidence references. An intent can be answered without a work item. Retrying creates a distinct attempt and reuses an effect key only for the same logical effect.
- **Grant** binds a principal and worker to a named operation, scoped effect targets such as paths or artifact IDs, intent version, time limit and budget. The host intersects caller, target, worker and task permissions and checks the result at dispatch and effect time. Plans, artifact content, worker capability reports and mesh messages are inputs to evaluation. Host policy supplies authority.
- **Event and evidence** carry schema version, actor, correlation identifiers, sequence within the work stream and timestamp. Evidence adds source identity, artifact digest, validation method, coverage and freshness. Artifact access is checked at retrieval. Events and diagnostics exclude secret values. Retain summaries and references according to host policy.
- **Client and worker operations** cover submit, steer, inspect, follow events from a cursor, decide, cancel and retrieve evidence. Workers register, claim, heartbeat, report and acknowledge termination. Mutations carry idempotency keys. A repeated key with a different payload produces a conflict. Negotiate schema and capabilities before dispatch.

A durable request advances from accepted to running, may wait for a decision or dependency, and ends as satisfied, partial, failed or cancelled. Attempts separately move through queued, leased, running and terminal states, with an explicit reconciliation state for worker loss or uncertain effects. Satisfied means the outcome criteria have recorded evidence. Receiving an artifact, a worker success response or a mesh acknowledgment alone is insufficient.

A decision refers to the intent version and exact action parameters, target and expected base state. Scope or state drift requires reevaluation. When steering or cancellation invalidates work, stop new claims and grants first, signal the active worker, and expose cancellation as pending until it is acknowledged or reconciled. Reject stale lease generations for finalization. Effect adapters declare whether they can enforce the active lease and grant at the target, directly or through a broker that controls the write path. A fenced target rejects stale generations and revoked grants before applying the effect. If the worker can bypass that path, report the effect as unfenced. When policy requires fencing, refuse that placement. For permitted unfenced effects, keep cancellation pending and block conflicting reassignment until the original worker's ability to act and any uncertain effect are reconciled. An action journal records effect intent and observed receipts. Retry a confirmed safe operation, reconcile an uncertain result, and preserve outstanding ambiguity if the external system has no way to resolve it.

A remote worker receives only scoped inputs, credential references resolved at authorized boundaries, and a bounded artifact return channel. Placement requires available capabilities and compatible enforcement. The coordinating service owns dispatch state for a given attempt. Mesh peers may coordinate independently, and worker partitions may leave an external effect unknown. Lease expiry permits reassignment only when the effect can be safely fenced, replayed or reconciled.

## Assignments and portable recovery

An assignment records required skills and expertise, resource bounds, execution window, compatible checkpoint formats and allowed inference routes, including provider, model and permitted data location when applicable. Placement checks runtime compatibility and current authorization separately. Before fallback or a route change, recheck policy, budget and checkpoint compatibility. Record the actual route per attempt and attribute usage by route.

The coordinating host owns durable checkpoints and artifact references independently of worker lifetime. A checkpoint records schema, intent and DAG versions, completed nodes, pending effects, workspace or artifact snapshots and the state required to resume. Explicitly identify worker-local or provider-session state and whether it can be exported. On another host, restore a compatible durable checkpoint, restart from the last safe step when state is missing or incompatible, or wait for reconciliation when effects are uncertain. Preserve evidence and fence stale attempts in each case.

## Worker capacity and provisioning

The scheduler can use existing enrolled capacity, request more capacity through a provider adapter, or report what is unavailable. A capacity request describes CPU, memory, accelerator, storage and runtime needs, isolation and placement constraints, expected lifetime, and a spend limit. Provider adapters expose supported options, estimated cost and lead time, and operations to provision, inspect, drain and release capacity. On-prem adapters can allocate resources from a managed pool. Cloud adapters can create ephemeral workers and account for credits or billed spend. Creating new capacity and dispatching work to it are separately authorized operations.

Distinguish service-owned ephemeral resources, leased slots in a shared pool and externally owned enrolled hosts. Record owner, release authority and provider identity. Release an owned resource only under its lifecycle grant, return a shared slot to its pool, and unenroll an external host without destroying it. Reserve capacity and spend before requesting creation. Persist an operation key before the provider call. After an ambiguous create or teardown, hold capacity and budget exposure until reconciled using provider identity or idempotency support. Where the provider cannot resolve the ambiguity, surface it for reconciliation before attempting another create. Enroll the worker with a scoped identity and verify its capabilities before dispatch. Show requested, starting, ready, draining, released and unknown states. Apply retention to artifacts separately from worker lifetime. Reconcile failed startup, expired leases and orphaned resources, and confirm release with the provider. Attribute startup time, idle capacity and provisioning charges to outcome measurements where applicable.

For the pilot, use a disposable worker with the operator's Docker cloud credits once the provider and available provisioning interface are confirmed. Run one bounded workload, record startup time, usage and credit consumption, then verify teardown. Exercise the same lifecycle against an on-prem adapter or a managed local pool.

## Workflow DAGs and gates

A process definition pins a DAG version, typed inputs and outputs, and nodes for human, model, tool or deterministic steps. Edges declare the outcomes that enable downstream nodes. A gate is a node that persists its decision and controls dependent work. Users can configure a human approval, a model review with explicit instructions, a deterministic check, any supported evaluator, or a direct edge with no gate. The host enforces applicable organization policy and action permissions independently of the process definition.

Validate acyclicity, edge conditions, input compatibility and join rules before starting. Persist completed node results and gate decisions. Bind each decision to its evaluator, input versions and the step or action it governs. On recovery, resume from recorded state and reconcile uncertain effects before retrying them. Failure, rejection, timeout and cancellation can route to explicit fallback, compensation, escalation or terminal nodes. Bounded retries create new attempts at a node. Revised plans or rework that would revisit earlier nodes use a new DAG run linked to the original. Distinguish a node timeout from an operator stop and from revocation. A timeout follows the configured DAG edges. An operator stop closes admission for new work on the affected intent, including queued recovery and compensation, and signals in-flight attempts. Record and reconcile effects already in flight. Revocation immediately invalidates the affected grants and stops dependent effects, while independently authorized work can continue. Recovery and compensation require current authorization and applicable gates at dispatch and effect time. After a stop, an operator can explicitly authorize a separate recovery run.

## Expertise graph

Each expertise entry has a stable ID and immutable version with provenance, applicability, prerequisites, relationship links, usable procedures and verification criteria. It may point to knowledge sources, tools, human roles or optional model providers. Dependencies identify compatible versions and can express prerequisites, alternatives or conflicting guidance. Record candidate, active, superseded and revoked versions separately from the versions pinned to an attempt. Activation identifies the applicable user or organization scope and workflow version. Supersession changes future selection. Revocation blocks further use within scope, including for pinned attempts. Retain prior pins for audit, stop affected downstream actions, reconcile effects already in flight and route to recovery or reevaluation.

For a given intent, identify the expertise required by the proposed steps and checks. Compare it with the entries available and permitted in the current context. Load the applicable subgraph into a general-purpose model or use its procedures through tools and manual steps. Record the selected versions and identify gaps by the affected step and the evidence needed to resolve them. Fill gaps through an eligible existing entry, a human contribution or a new version activated under the configured workflow. Reevaluate affected steps after a change and retain prior provenance.

Users can ask Ozagia to build expertise for a domain or a recurring workflow. Specify the scope, source and research policy, authoring model, and budget of the research run. Ozagia can use a frontier model to compare sources and produce a reviewable candidate graph entry with attributed claims, disagreements, prerequisites, decision rules, worked examples, checks and known limits. Users can also create or edit entries manually. The configured workflow determines whether a candidate activates directly or passes through gates first.

At use time, assemble a task-specific slice of the active expertise. A less capable model can follow its procedures and invoke its checks without repeating the original research or calling the authoring model. The intended savings come from reusing the research across runs. Updates and verification still carry costs. Evaluate transfer on held-out tasks by comparing a lower-cost model with and without the expertise and using the frontier model as a reference where practical. Use expected outcomes and checks sourced independently of the authored expertise, including cases that should surface a gap or escalate. Record authoring, review and update costs alongside per-run usage and verification effort to estimate how many successful reuses repay the investment. This evaluation is distinct from any activation gate the user configures.

Dynamic retrieval is a later capability. A configured registry may provide expertise graph packages and references to optional specialist models. Verify origin, integrity, dependency compatibility and policy before activation. Treat executable tools or model access as separate capabilities with their own grants and budgets. In-flight work retains pinned versions across routine updates. Revocation follows the stop and recovery rules above.

Apply per-attempt limits, cumulative intent limits and any recurring service allowance together. Renewal replenishes only the recurring allowance. A budget owner reserves usage before dispatch and allocates bounded sublimits to delegated work. Peers enforce the delegated limit before issuing calls, and retries draw from the same parent budget. Commit actual usage once per attempt and release unused reservations after reconciliation. Carry unresolved reservations across renewal and deduct them from available capacity until reconciled. Charge a late or duplicate receipt at most once against its original reservation and period. Release the carryover when settled. If policy closes an unresolved reservation without a receipt, account for its maximum reserved spend and reconcile any later receipt against that charge. Propagate graph-only and zero-model constraints through every delegated step. A peer that cannot enforce the applicable limits is ineligible.

## Ozma inference request

Ozma owns the wire contract for requesting and returning inference. Ozagia is both a requester and a provider through its graph and reasoning adapters. A peer can request inference independently of a remote agent run or a project. For example, it can ask which outcomes depend on an instrument whose calibration changed. An authorized graph peer can derive a bounded answer from typed relationships and return evidence without using model inference.

- **Request.** Carry a request ID and schema version, a typed question or goal, scoped input and graph references, expected result shape, freshness and provenance requirements, deadline, and resource limits. The requested fulfillment policy can permit graph-only, model-backed or hybrid execution. Zero model budget prohibits model calls, including fallback. A model can also issue graph-only requests as part of a larger run.
- **Capability and routing.** Peers advertise supported inference kinds, result schemas and fulfillment modes. Resolve identity and allowed data scope before forwarding. Execute graph operations through a provider-supported interface over an authorized view. Graph content and returned conclusions carry evidence and confer no authority to act.
- **Result.** Return a typed answer or artifact with the actual fulfillment mode, graph and snapshot references where disclosure is permitted, relevant supporting evidence, uncertainty, omissions and metered usage. Distinguish complete, partial, unavailable, denied, failed and cancelled results. A peer can acknowledge receipt without claiming that it has fulfilled the request.
- **Lifecycle.** Support status and cancellation for asynchronous requests. Scope request IDs to the authenticated requester and compare payloads on duplicate delivery. Recheck current access on status, replay and artifact retrieval before exposing results or metadata. Initial interoperability should verify one authenticated request between two peers, cancellation and replay, and redaction across different visibility scopes. Pin the Ozma contract used by the bridge and report unsupported capabilities.

## Model-facing configuration

Expose a configuration skill backed by the canonical settings registry. For every item, expose its meaning, types, units, allowed values, supported scopes, defaults, current effective value, precedence, dependencies and writeability under current policy. Include settings supplied by adapters through the same contract. For credentials, expose reference types and presence without exposing secret values. The skill uses typed inspect, propose and apply operations shared with manual configuration. It can act directly where authorized or route the proposal through configured gates.

Translate natural-language requests into reviewable changes with effective scope, consequences and the current configuration version. Validate cross-setting constraints and apply changes atomically against that version. Authorize the entire proposal and any bundled actions under the policy in force before the change. A proposal cannot use a gate removal or permission increase to authorize itself or a bundled action. Bind approvals to the exact proposal and policy version, and invalidate them when either changes before apply. Route any later operation through the resulting effective policy. Show conflicts, unsupported capabilities and settings overridden by higher-level policy. Record what changed and provide a scoped rollback where supported. Treat inferred preferences as proposals where the user has not authorized a change.

For “I don't want my agents to use more than 80% of my five-hour allowance,” identify the allowance, its unit and reset window, and which agents and inference routes share it. If context identifies a five-hour provider quota window, cap usage at 80% of the provider-measured allowance within that window. If it identifies five hours of compute time, the cap is four hours. Ask only when the distinction or scope would materially change enforcement. Use actual usage and outstanding reservations. If the provider offers insufficient quota information for a hard limit, explain what can be enforced and label any estimate.

## Adaptive provider allowance estimates

Maintain a versioned estimator per provider, subscription or shared quota pool, model, and allowance window type. Join timestamped provider allowance readings and resets with metered run logs. Capture input, cached input, output and other token classes where available, request counts, execution phases, and concurrent assignments. Calculate cache hit ratio when the provider exposes a meaningful numerator and denominator. Keep raw units and missing fields explicit. Report estimated allowance consumed per token class, or an effective allowance-to-token ratio for the observed workload mix when separate coefficients cannot be identified.

Fit shared-window changes jointly across overlapping runs. An observed drop belongs to the quota pool and cannot be charged in full to each worker. Identify resets, delayed or coarse readings, and untracked use. Show unexplained usage and report when there is too little variation to distinguish models, token classes or cache effects. Token logs alone cannot establish the provider's allowance conversion without a corresponding allowance observation. Retain a fallback estimate only with its assumptions visible.

Weight recent observations more heavily with configurable decay. Track prediction error against subsequent readings and flag sustained drift. When the provider, model or quota rules change, lower confidence, start a new calibration segment where appropriate, and preserve the previous segment and its estimates for comparison. Expose current estimates, ranges, calibration age, sample coverage, observed versus predicted consumption, cache mix and historical changes through the operator view and programmatic interfaces. Scope detailed logs to the host's access policy.

Use the estimate and its uncertainty to reserve expected allowance for dispatch. Prefer authoritative provider usage and limits when available. Identify every applicable limit, including account, subscription, model and overlapping rolling or fixed windows. Reserve against all applicable limits in one admission decision. If any reservation fails, admit no work and leave no partial reservation. When readings are stale or missing, apply the operator's configured treatment for each affected limit. Defer when a required hard cap cannot be enforced. Where policy permits estimates, account for uncertainty and outstanding reservations and expose which limits are estimated. Show whether an allowance policy is provider-enforced, conservatively estimated, or unsupported. An estimated conversion cannot guarantee a hard provider cap. Apply the configured treatment of uncertainty before dispatch, including deferring work when a strict cap cannot be enforced.

## Workflow experience and progress

A person can state an intent, inspect the current plan and change direction, answer a gate or stop work from the same context. Show the outcome and its evidence first, with steps and attempts available for diagnosis. Present blockers with the reason and available actions. Use plain descriptions for queued work, retries and recovery. The detailed DAG remains available through the UI and other entry points.

Build progress from authorized events and recorded criteria. A deterministic update can report the last verified milestone, active work, a blocker and the next expected step. Use a timestamp and distinguish an estimate from a recorded fact. When the scope can change, show milestones and remaining known work. A percentage is appropriate only when the denominator is known. An optional model can summarize the structured snapshot in natural language, within a separate update budget and audience scope. The summary links to evidence, preserves caveats and leaves execution state to the underlying records. Fall back to the deterministic update if the model is unavailable or its response cannot be grounded. Coalesce routine events and surface decisions, material changes and verified milestones promptly.

## Messaging and ChatOps

A messaging adapter declares the capabilities of its harness, such as direct messages, channels, threads, commands, replies and interactive controls. Through the same service operations used by other clients, a person can submit an intent, ask for status, steer or stop work, or respond to a gate. The workflow binds each response to its decision. Require verified sender identity only where the configured policy requires it. Adapters can support updates alone or full two-way interaction. An unsupported control can link to an authorized view for completion.

Allow the operator to configure trusted channels or senders, shared principals, or per-user verification for specific operations. Map available sender and destination identities to principals and audiences under that policy. Apply configured event verification and deduplicate deliveries before starting work or recording a decision. A channel, mention or forwarded message can authorize only what the configured policy grants it. Bind each actionable response to the current intent version and decision. Apply current permission checks before acting. An unsolicited message can be context, and a valid command or explicitly addressed request can initiate work according to channel policy. Independently of identity verification, operators can configure which workflows an intake route or shared principal may start, plus optional limits on starts per window, concurrent runs and spend. Apply those limits at admission across distinct deliveries and return a clear queued or declined state according to policy.

Route progress, milestones, blockers and requests for input to configured destinations using the same materiality and batching rules as Home. Check what the destination audience can see before rendering or sending an update, including links and summaries. Preserve delivery status and retry without promising exactly-once delivery on transports that lack it. Messaging outages leave workflow state available through other clients and consultation deadlines follow the configured DAG.

## Calendars and scheduled events

Maintain a reference calendar with native events and links to external events. Support milestones, deadlines, review windows, staffing availability, resource bookings and recurring schedules. An event can relate to multiple projects or standalone intents without being duplicated. Show relevant upcoming events and changes alongside active work. Expose calendar data through the UI and the same programmatic interfaces used by other clients.

Adapters declare support for reading, watching and writing events, and for availability-only queries. Preserve the source of each event, its identity and revision, time zone, recurrence and exceptions, and when it was last refreshed. Apply configured access and audience policy. Use availability-only data when event details are unnecessary. Distinguish unknown or stale availability from confirmed availability. External calendar writes follow configured policy and detect conflicting changes where the adapter supports it.

Workflows can subscribe to configured calendar conditions such as an event approaching, a schedule changing or a booking ending. Give each occurrence a stable source-scoped identity across reschedules and track its observation revisions separately. Deduplicate trigger evaluations by occurrence, rule version, relevant revision and trigger kind. Ignore older observations and retain cancellation markers for reconciliation. If the source cannot order observations reliably, reconcile against its current state before starting revision-sensitive work. On change or cancellation, invalidate stale pending triggers and reevaluate queued work. Apply the configured steering or cancellation policy to running work and preserve evidence of completed effects. On restart, reconcile current occurrences before applying the rule's configured catch-up policy. Support elapsed offsets and local wall-clock schedules with explicit time zone and daylight-saving behavior. Calendar events provide context or trigger evaluation under standing policy. Any resulting action follows the configured DAG and permissions.

## Attention and unattended operation

Before asking, identify the decision, the plausible answers and what would change. If the difference is immaterial or can be resolved within standing policy, proceed and record the assumption. When asking, supply the relevant evidence, options and consequences of waiting. A notification should explain why the information matters now. Batch routine changes under the user's preferences while keeping current status, history, DAG decisions and detailed evidence accessible on demand.

A consultation may be advisory or required. For advisory consultation, the workflow can continue independent work while it waits and take a specified default or recovery branch at the deadline. A required gate stays closed until the required decision arrives. If it times out, only an explicitly authorized branch can run, such as deferring the affected work, escalating or continuing elsewhere in the DAG. Silence alone never grants authority. Record the timeout and chosen branch. Late replies can inform subsequent work, with completed effects visible.

A service can operate indefinitely under standing policy with durable state, bounded attempts and resource budgets that renew only as configured. It can recover after restart, continue unrelated work around a blocked node, and wait for relevant events when no work is ready. Operators can inspect, steer or stop it when they return. Record requests for attention, time spent waiting for human input, and human effort where observable. Evaluate reduced interruptions alongside verified outcomes and decisions escalated on time.

## Outcome efficiency and model comparison

Record one measurement per intent and retain its attempts and contributing steps. The outcome records criteria satisfied, partial results, quality against a task-appropriate rubric, and the evidence used to judge them. Capture raw inputs independently of outcome. Include model and provider versions, input, cached and output tokens where available, actual billed or estimated cost with pricing basis, tool or compute usage, human effort and review, retries and escalation. Distinguish unknown values from zero. Attribute model-generated updates and shared expertise authoring separately so operators can see both marginal run cost and amortized cost under an explicit reuse assumption.

Measure end-to-end elapsed time from intake to verified outcome. Break out queueing, active execution, external dependency waits and time waiting for a decision. For parallel work, report elapsed time separately from summed worker time. Let operators compare time to usable outcome and apply their own value to delay or missed deadlines, alongside direct spend.

Compare models on matched requests with comparable starting evidence, expertise versions, tools, rubric and policy. Record warm and cold runs, configuration differences, sample size and failed or cancelled attempts. Publish verified completion rate, quality, cost per verified outcome and elapsed-time distributions alongside raw token counts. Include the cost of unsuccessful attempts in aggregate cost per verified outcome. Compare dimensions before applying any operator-selected weights. A higher per-token price can yield lower total cost if the model reaches a verified outcome with fewer calls, tokens, retries or reviews.

## Forecasting from observed work

Store forecasts alongside actual run measurements. Use comparable work based on scope, outcome criteria, workflow, domain, model, expertise version, execution environment and human dependencies. Distinguish model and tool execution time from elapsed delivery time and human effort. Historical human project durations can inform human-dependent steps when relevant. Use measured agent runs for agent execution estimates and label each source.

Ozagia can compute a baseline forecast without a model. With sufficient comparable runs, report a typical value and a prediction range for elapsed time and, when supported, cost and likelihood of verification by a deadline. Show the cohort, sample size, recency, assumptions and gaps. Label duration among verified runs separately from the likelihood of verification by a deadline across all comparable starts. Failed and cancelled runs count as unsuccessful for that deadline cohort and contribute their observed time to stop, while runs still in progress contribute only their known follow-up. Account for incomplete follow-up or omit the probability when it cannot be estimated reliably. Report cancellation policy and sample coverage. Where data is sparse or stale, widen the range or report insufficient evidence. Label manually supplied or heuristic assumptions separately from measured baselines.

For a project or workflow forecast, use dependencies, available concurrency and measured wait times, including approvals and external work. Parallel branches contribute to elapsed time through the paths that determine completion. Shared resources, retries and recovery paths may change those paths. Incorporate relevant staff availability, holidays, review windows and resource bookings from the reference calendar. Report the source, freshness and assumptions. Free calendar time is a scheduling signal. Treat unconfirmed availability as uncertainty and reforecast when relevant events change. Reforecast when scope, progress, model or staffing changes. Keep the original and revised forecasts with their timestamps so the operator can see what changed and why.

Provide the same scoped forecast and comparable-run summaries to models through the workflow interfaces. A model can explain the estimate or propose an adjustment with explicit assumptions. Preserve that adjustment separately from the measured baseline. Backtest against later runs using only evidence available when each forecast was made. Track systematic bias, error and how often actual outcomes fall within the stated ranges. Compare against a simple historical baseline and reassess calibration when model versions, tools or workflows change.

## Optional telemetry and pooled estimates

Telemetry is off by default. An operator can enable it within the applicable organization policy, preview a sample payload, and turn it off. Disabling stops uploads and clears pending telemetry. Use a versioned allowlist for locally aggregated or bucketed measurements such as public model and provider versions, token usage, elapsed and active time, retries, broad workflow category and verified outcome status. Exclude prompts, outputs, evidence, graph content, filenames, project and user identifiers, secrets and private model names. Before upload, suppress private and deployment-specific dimensions and bucket or omit sparse local combinations using published schema rules. Avoid persistent installation identifiers. The receiver validates the allowlist and applies separate publication rules, including a documented minimum observation threshold and suppression of sparse or overlapping cohort slices that could expose individual contributions through differencing. Keep request bodies and source addresses out of telemetry storage and routine access logs. Document any necessary transient network handling and the retention and expiry of received batches and published aggregates. Opt-out clears queued local telemetry and stops future uploads. Previously accepted batches expire under the published retention policy, and published aggregates follow their own retention schedule.

Use pooled measurements as a labeled baseline when local data is sparse, and keep their source, age and sample coverage visible. Compare them against local results before relying on them for forecasts or routing suggestions. Account for differences in workloads, model versions and who opts in. Changes to automated routing remain governed by local policy. Fetching aggregate statistics and contributing telemetry have separate settings.
