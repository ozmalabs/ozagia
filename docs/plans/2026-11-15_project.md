# Graph dev tooling as its own project: plan

Status: plan. `<project>` is a placeholder until the name is chosen. Base:
Ocelot `main` at f2ccaeaa. This plan supersedes the layout of
`DEV_TOOLING_V3_GRAPH_AGENT_PLAN.md`. That plan's verified probes (its W0) and
its intent-mapping table still hold, and are referenced here, not copied.

## What the project is

A public, MIT-licensed framework that lets an LLM agent work on a code
**graph** instead of on files and lines. It covers indexing a repository into
a typed graph, keeping that graph live while the agent edits, and putting it in
the agent's path.

It does that at three depths, so it can run a whole harness and also fit into
tools people already use:

| depth | what it is | features |
|---|---|---|
| **Library** | Python API: graph, queries, edits, checks, intents. Use it from any agent loop. | all |
| **Integration** | Plugs into an existing tool. OpenCode: a plugin that captures `read`/`grep`/`edit`/`shell` and carries out their intent on the graph (verified on 2.3.0). Claude Code: hooks that can rewrite or block calls and add context, but not replace a built-in's result. Any MCP client: graph tools offered next to the built-ins. | OpenCode full; Claude Code partial; MCP tools only |
| **Harness** | `<project> agent`: a complete agent session on a repository. It drives OpenCode headless (`opencode serve` plus the plugin and the graph daemon), with a small native Python loop for controlled experiments. | all |

The capability gap between integrations is stated per feature (see the
matrix), not hidden. A user with Cursor or Codex gets the MCP tier and knows
what is missing.

### Harness: integrate first, fork only on evidence

OpenCode is MIT-licensed ([LICENSE](https://github.com/anomalyco/opencode/blob/dev/LICENSE)),
so forking is allowed. But its plugin API already gives full tool capture
(probe 1 in the v3 plan), and upstream moves fast: the v1→v2 plugin change
broke existing plugins. A fork would mean carrying a TypeScript/Bun codebase
against that churn. So:

- The full harness **integrates** OpenCode: server mode, our plugin, our daemon,
  a generated config. No fork.
- A **native loop** (one Python module, OpenAI-compatible API, the same intent
  layer behind the same four tool shapes) gives full control for experiments,
  and can point at any endpoint, including an ozma-ai proxy.
- **Fork gate:** fork only if a needed behaviour cannot be done through the
  plugin API, for example the system prompt, compaction, or the tool list
  itself. Record the blocking case before forking.

### Relationship to Ocelot and ozma-ai

- **Ocelot** becomes the first target repository. It keeps an **adapter**
  (seed and rule indexer), its task suite, and the parts that need its runtime
  (`ocelot_ir_edit.py`, `graph_interrogate`). It installs `<project>` and
  keeps its MCP config working.
- **ozma-ai** works at the proxy, between client and model, and cannot change
  what a tool does to the files. `<project>` works inside the agent. They fit
  together: graph deltas could feed ozma-ai's output checks, and the native
  loop can run through the ozma-ai proxy. Integration is decided after the
  pilot. ozma-ai's own `code_search.py`, `blast_radius.py` and `apply_patch.py`
  are text-level and are not reused.

## Architecture

```
<project>/
  core/          graph model (nodes, edges, stable keys), store, snapshot,
                 incremental reingest, queries (search, expand, impact),
                 symbol graph, repo map
  index/         indexers: tree-sitter tags (existing languages), Python CST,
                 Markdown, JSON, text chunks; plugin interface for repo adapters
  edit/          edit transaction, lossless text, structural ops, span->node
                 edits, graph deltas
  check/         test runs mapped to symbol keys (pytest first)
  lsp/           optional language-server refinement
  intent/        tool call -> intent -> graph operation -> rendered result;
                 harness-neutral; one renderer per target tool schema
  integrations/
    mcp/         MCP server (the existing one, plus a small "graph" surface)
    opencode/    plugin (JS, no npm dependencies) + daemon client
    claude_code/ hooks (partial capture)
  daemon/        per-workdir process holding the graph warm; Unix socket
  harness/       `<project> agent`: OpenCode driver + native loop
  eval/          break/fix harness (the current ocelot_agent_eval), arms,
                 drivers, target suites
```

Per-repository configuration, `.<project>.toml` in the target repo: source
roots, doc globs, skip directories, adapter entry points, test command. The
defaults index any Git checkout. Ocelot's file lists its directories and its
seed adapter.

### Capability matrix (the target; each cell becomes a test or a "not supported" line in the docs)

| feature | library | OpenCode plugin | Claude Code hooks | MCP only | native loop |
|---|---|---|---|---|---|
| graph queries (search, expand, impact) | yes | yes | yes (MCP) | yes | yes |
| `read`/`grep` answered from the graph | yes | yes | no: can add context after the built-in runs | no | yes |
| `edit` applied as a node edit, with delta | yes | yes | partial: rewrite input or block before; delta added after | via graph tool only | yes |
| `pytest` returned as per-test, per-symbol results | yes | yes | context after the built-in | via graph tool only | yes |
| graph live after every edit | yes | yes | yes, reingest in the after-hook | only for graph-tool edits | yes |
| fallback to the built-in when the daemon fails | n/a | yes | yes (built-in runs anyway) | n/a | n/a |

## Waves

Executors: the `ocelot-substrate-executor` agent is scoped to Ocelot's
substrate. W0 creates a `<project>-executor` agent with the same discipline
(own worktree, disjoint write scope, never commits, task report) for the new
repository. The supervisor merges, gates and commits, as before.

### W0: extract and bootstrap (sequential, supervisor-led)

1. **Public-release audit** of everything that moves: absolute paths
   (`/applications/...`, `/home/matt/...`), hostnames, keys, private notes,
   and commit messages in the moved history. Anything found is fixed in Ocelot
   first.
2. **New repository** with history: the dev-tooling files and their tests, cut
   with `git filter-repo` (installed with pip; it is not installed now) into
   `~/ozmadev/<project>`. The package gets the layout above. Imports go from
   `scripts.ocelot_x` to `<project>.<module>`. A `pyproject.toml`, MIT
   `LICENSE`, `README.md`, an `AGENTS.md`, and GitHub Actions running pytest
   and ruff.
3. **Remove the runtime dependencies:**
   - Replace `domains/py_cst_ingest` (used by `ocelot_lossless.py`) with a
     standard-library tokenize leaf producer. Equivalence test: identical
     leaves on every Python file in Ocelot.
   - Move the hard-coded roots, doc globs, skip lists and path regex from
     `ocelot_dev_memory.py` into config.
   - Move the seed/rule/concept/production indexing behind the adapter
     interface.
   - Leave `ocelot_ir_edit.py` and the `graph_interrogate` bridge in Ocelot.
4. **Ocelot side:** an `ocelot_devtools_adapter` (the seed indexer), `.<project>.toml`,
   an editable install in Ocelot's venv, and thin shims, so that
   `.opencode/opencode.json` (`scripts.ocelot_dev_memory_mcp`) and the
   documented CLI commands keep working. Then remove the moved modules from
   Ocelot.
5. **Gate:**
   - The 428-test gate passes, split between the two repositories.
   - A snapshot of Ocelot built by `<project>` plus the adapter equals one
     built by the current code, apart from timestamps.
   - Bench targets from v2 still hold: warm repo_map ≤ 1.0 s, code_search
     ≤ 0.5 s, impact ≤ 0.3 s, cold index ≤ 30 s.
6. Create the GitHub repository under ozmalabs. **Push only after you approve
   the audit result.**

### W1: a graph that stays live (parallel)

The v3 plan's W1-A (stable keys and incremental reingest), W1-B (span→node
edits and deltas) and W1-C (test runs and text nodes), now in `core/`,
`edit/`, `check/` and `index/`. W1-D (8 harder tasks) goes into Ocelot's
target suite.

### W2: intent layer and integrations (parallel)

- **W2-A intent + daemon:** the v3 intent-mapping table in `intent/`, served
  by `daemon/`. The rendered output is per tool schema, so the same intent
  serves OpenCode, Claude Code and the native loop.
- **W2-B OpenCode plugin:** the v3 W2-B plugin, in `integrations/opencode/`.
- **W2-C Claude Code hooks:** a PreToolUse hook that rewrites a captured `Edit`
  into a node edit, or blocks it with the result. A PostToolUse hook that
  reingests the file and adds the graph delta and headers as context. Tests
  with recorded hook payloads. Live-untested until Claude is logged in.
- **W2-D MCP graph surface:** the v3 verbs (`find`, `node`, `expand`,
  `impact`, `edit`, `create`, `check`, `note`) as a small surface (total tool
  descriptions ≤ 1,500 tokens). The existing 43 tools stay available.

### W3: harness (parallel)

- **W3-A `<project> agent` on OpenCode:** prepare the workdir (clone, index,
  daemon, plugin, generated config) and run `opencode run` or an interactive
  session. Clean up afterwards. This is the agent-eval harness's live path,
  turned into a user-facing command.
- **W3-B native loop:** a minimal loop over an OpenAI-compatible API with the
  four tool shapes, backed by `intent/`. Time limits, a cost cap, transcripts
  in the eval format.
- **W3-C eval:** the eval harness gains drivers `native` and
  `opencode+plugin`, and the target-suite format (repository, base commit,
  tasks). Ocelot's 15 tasks are the first suite.

### W4: supervisor

Merge, gate, semantic review, docs (README with the capability matrix,
quick-starts for each integration). Then the pilot on the Ocelot suite, local
model, $0:

| arm | what it tests |
|---|---|
| baseline | OpenCode, no graph |
| mcp | OpenCode + MCP graph tools (v2's dev_memory arm) |
| opencode_intent | OpenCode + plugin (full capture) |
| native_intent | native loop + intent layer |

4 arms × 15 tasks × 3 repeats = 180 sessions, about 4 hours. The v3 plan's
metrics and failure labels apply.

## Open decisions

1. **Name.** The package, CLI, config file and GitHub repository all take it.
2. **Ocelot's own licence.** Ocelot is public but has no `LICENSE` file. The
   extracted code will be MIT. Ocelot should get a licence too, or at least
   the moved history should be covered.
3. **Hosted model** for the pilot: stays local-only unless you approve a
   hosted arm with a cost cap.
