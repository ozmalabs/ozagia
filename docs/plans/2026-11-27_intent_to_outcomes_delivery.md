# Ozagia intent-to-outcomes staged delivery plan

2026-11-27. The [product specification](../intent_to_outcomes_spec.md) governs behavior. This plan gives each stage a usable increment and an exit test. Stages are dependency milestones, with no calendar or release commitment.

## Architecture direction

Treat workflow as a graph-native operation in the existing Ocelot/Ozagia substrate, rather than introducing a separate DAG engine and parallel workflow model. The graph is the canonical record of intent revisions, assignments, dependencies, attempts, effects, decisions and evidence; progress and UI views are derived from it. Execution is available through the graph but is never implied by graph presence or visibility.

Reuse Ocelot's Rust-backed `substrate_rs` graph storage, typed graph API, graph persistence, scoped aperture/frame concepts, and graph-resolved action/commitment patterns where their guarantees fit. Extend Ozagia's existing replayable session graph and adapters behind a narrow supported interface. Ocelot's current dev-session graph is a receipt graph, not a complete durable effect executor; this plan must add workflow lifecycle and recovery semantics rather than assuming those already exist. Keep Ozagia as owner of intent lifecycle, project binding, policy, evidence provenance and integration behavior. The effective aperture combines what an actor can see with what they may do, scoped by identity, linked projects, intent revision, assigned capability and applicable approval. Resolve it for each requested operation at the point of effect, and record the attempt, result and evidence in the graph. Revocation or revision changes must invalidate stale authority. Use target fencing/idempotency where available and explicit uncertain/reconciliation states where exactly-once effects cannot be guaranteed.

Make the UI a lightweight, dynamic projection of the same scoped graph, not a second workflow state model. Define a small versioned view contract for nodes, typed relations, status, available operations and evidence references. Present a compact accessible work list by default, with graph exploration when useful. Render known node and operation types with reusable components and provide a readable generic fallback for extensions. The UI may request an operation but never authorizes it; the backend resolves the effective aperture and records the result. Keep presentation state separate from canonical workflow state.

Prefer the existing Python integration and adapter layer for the pilot while using the Rust-backed graph store. Measure total resident memory and process count on the representative workflow, including idle and active states. Consider a Rust worker/runtime boundary only if it reduces the actual integrated footprint or materially simplifies deployment without duplicating the graph, policy, or adapter model. Keep graph and operation contracts versioned and language-neutral so such a boundary remains possible.

### Decision manifolds

For an LLM worker, test the hypothesis that stochastic generations are effectively deterministic at a declared outcome resolution within a particular frame. For example, different wording, tool sequences and patches may all implement the same requested change and seek the required review. Define in advance which differences matter, including failure, an attempted unauthorized effect and escalation. Record the model revision where available, sampling configuration, instructions, conversation, visible evidence, tools and workspace snapshot. Treat any hidden provider state as a limit on reproducibility.

For a fixed intent, test the hypothesis that a need for corrective steering during execution exposes a defect in either the initial conditions or the scaffolding. Initial conditions describe what the worker starts with, including its context and the starting workspace. Scaffolding describes how the run proceeds, including tool contracts, evidence retrieval, verification feedback and escalation rules. A planned human decision belongs to the scaffold; a new user objective starts a new intent revision. Count a rescue needed to meet the original criteria even when the rescued run ultimately succeeds.

Evaluate an outcome by the useful continuance it creates and how far that advances the overall goal. For exploratory work, record the question and the downstream decision it bears on before the run. At review, compare what the operator could usefully do before and after the result. Evidence may enable a next step, eliminate an unproductive course or justify stopping an investigation. Record the specific consequence and its evidence, measuring time or work saved where there is a defensible baseline. Distinguish anticipated usefulness from subsequent use. Keep the need for corrective steering as a separate measure of execution quality.

Before dispatch, Ozagia constructs the worker’s initial decision landscape. Given the intent and success criteria, select the evidence, context, tools and standing instructions the worker will receive. Record why this arrangement is expected to make acceptable histories reachable and likely, and which alternatives it may foreclose. Pin the prepared inputs and the prediction before the worker’s first inference or tool action. Leave the ordinary run uninterrupted so its trajectory reveals the consequences of that preparation.

At Stage 0, define the usual starting frame, outcome classes, a stability threshold, and a sampling budget. At Stage 1, prepare two starting frames for the same task and workspace. For example, place evidence of a legacy caller in one initial context while keeping the requirement, tool permissions and independent compatibility check identical. Predict the difference before dispatch. Sample fresh runs from both frames, record proposals before enforcement and verify resulting artifacts. Report variation within each frame, the difference between frames, and exceptions. Test the prediction on a held-out change. Use recorded runs for offline analysis; fresh model runs require the existing live opt-in and approval.

Use the main Seldon construction as the design reference. From the current frame, project reachable histories over a declared horizon and resolution. Generate each next transition from its hypothetical predecessor, including represented external conditions such as reviewer availability. Mark the subset of histories satisfying the intent criteria, including constraints that must hold throughout. At a steering point, show which acceptable futures each intervention opens, preserves or closes, and where the continuing course first departs from a required bound. Preserve uncertainty when the projection budget runs out. [Main Seldon manifold paper](../../../graphic-equalisation/papers/formal/02_seldon_manifolds_theory_referenced.tex)

At a material steering point, use the graph to answer “From here, what can we do, and what outcome could each course reach?” Frame the decision with the current commitment, intent revision, target criteria, decision horizon and observable workspace state. Include continuing the current course. Generate alternatives from the actual capabilities, constraints and evidence in that frame. For each represented course, identify prerequisites, authority required, expected consequences across the criteria, and the evidence or uncertainty behind that expectation. Account for criteria jointly. Two criteria may each be achievable on different paths while no known path achieves both. An incomplete search can leave reachability unknown.

For each frame, identify whose decision is being described, the action in question, and the installed rule or commitment that will carry work forward if nobody intervenes. The paper’s aperture describes what enters that actor’s representation. Ozagia’s authorization check answers whether a principal may perform an operation. Keep separate records for a course considered and prohibited, a permitted course beyond current capacity, and a possibility first discovered in hindsight. A proposal shown in the UI changes execution only through a recorded change to a commitment, gate or other condition used by the executor. Record the trigger and cost of reopening a decision when measurable.

The operator can retain the commitment, choose a feasible alternative, request evidence or revise the target. Preserve the frame used at selection. Link the commitment to the attempted action, the observed effect and subsequent verification. New evidence can reopen the decision. This lets review distinguish a poor forecast, an implementation failure and a correctly anticipated trade-off. Keep the pilot representation finite and local to the steering point. Reuse the graph decision, revision and evidence records and apply the existing effect-time authorization contract.

This adapts Graphic Equalisation’s account of continuation, horizon, feasible selection and realised outcome, and Ocelot’s finding that scoring fixed alternatives on largely invariant axes produced choices insensitive to the situation. ## 0. Select and baseline one real workflow

Use a Dev Manager change-and-review workflow as the initial candidate. Pick a small real change with a clear verification recipe, a review artifact and one point where the operator can meaningfully steer. Capture the usual process first, including preparation, outcome quality, inputs, elapsed time, interruptions and time to regain context. Agree on outcome criteria and a comparable case before the pilot.

Pin the Ozagia, Ocelot substrate and harness versions. Inventory existing task, goal, graph, session, settings, aperture/action and review interfaces; map which can be reused directly, which need a narrow adapter, and which guarantees are absent. Validate the graph-native workflow direction against a separate DAG runner, including crash recovery, revision binding, revocation, effect replay and graph migration. Check exact workspace-to-graph binding. Record idle/peak resident memory and process count for the integrated workflow, plus a Rust-worker comparison only if it can be measured without changing the workflow. Sketch the UI graph projection and verify it can support a list-first interface and generic extension rendering. Use a private harness instance or scoped context adapter until shared-server capture is demonstrated. Keep Dev Manager responsible for its existing validation and delivery during the pilot. The [internal integration proposal](../../../internal/dev-manager/OZAGIA_INTEGRATION_PLAN.md) and [OpenCode smoke](../../../internal/dev-manager/OZAGIA_OPENCODE_SMOKE_2026-11-27.md) are starting evidence.

Before dispatch, capture the usual worker inputs and identify one change to their preparation with a predicted downstream consequence. At the baseline review point, record what the reviewer believed was possible, what continuing would do, and which observation could change the choice. Retain the eventual outcome for comparison.

**Exit.** A named workflow, recorded baseline, isolated test workspace, pinned interface choices and an ownership map for intent, graph state, aperture resolution, effect execution, review and delivery. The Ocelot reuse map identifies proven guarantees and gaps; the graph-native approach is accepted or rejected against the separate-runner alternative with reasons. Memory and UI projection baselines are recorded.

## 1. Deliver a local outcome and prove recovery

Ship one conversational path and a manual invocation of the same workflow. Support direct answers and durable standalone intents. Persist intent revisions, assignments, attempts, effects and evidence as typed graph records. Extend the existing graph/session operations for dependencies, a configurable gate, an error path and restart recovery; do not create a second canonical DAG model. Resolve visibility and operation permissions through the effective graph aperture, bound to the current intent revision and project scope, at each effect. Reuse the edit transaction and existing validation tools, and import their evidence with source identity. Define effect receipts and safe replay/reconciliation behavior for the pilot adapter.

Give Home or the existing host view a compact accessible list of active work, decisions and verified outcomes, projected from the scoped graph. Define the versioned UI view contract for status, relations, available operations and evidence references; retain a generic readable rendering for unknown types. Derive progress from recorded state and let the operator inspect evidence, steer and stop. UI requests pass through backend aperture resolution. Instrument time, cost, required decisions, interruptions and process memory from the first run.

Exercise the same steering point twice. With a current passing verification, proceeding to review is feasible. With a changed base and the same target, show why verification must be renewed, the effect on the expected delivery time, and whether the deadline remains reachable. The reviewer can inspect both frames and trace the selected course to its actual result. Include a case where the deadline arrives before verification and record the unmet criterion.

Hold the available actions fixed in a second fixture. Display a suggestion to seek another review and confirm the existing commitment still governs dispatch. Then have the operator accept the suggestion and install a required review gate. Trace the changed dispatch to that gate, record the review effort, and compare the realised outcome with the expectation recorded before review.

For the reachability exit, keep the initial menu fixed and project through the review deadline under two recorded conditions: a reviewer becomes available before the cutoff or only after it. From each successor apply the actual review and delivery rules. The fixture must distinguish a verified, reviewed delivery by the deadline, a missed deadline, and an inadmissible attempt to bypass required review. Check these classifications against the fixture histories and trace the realised run to evidence. A projection cut short before review reports unknown.

**Exit.** Report whether the paired initial frames produced the predicted difference on the held-out change, including uncertainty or an inconclusive result. For an experimental outcome, identify the downstream decision it changed or the next step it enabled and explain the contribution to the overall goal. Record pending downstream use explicitly. Report how often the original criteria were met without corrective steering and how often rescue was required. For a rescue, record what the operator supplied and when. On fresh matched runs, test a change to the initial conditions with the scaffold held fixed, or a change to the scaffold with the initial conditions held fixed. If both changes appear necessary, test their combination. Retain an unresolved attribution when the evidence cannot distinguish the causes. The operator reaches a verified outcome on real Dev Manager work, compares attention and interruptions with the usual process, and successfully recovers from a restart or interruption. Verify that changed revisions and revoked apertures invalidate stale authority/evidence, and that replay does not duplicate a fenced effect (or enters explicit reconciliation when fencing is unavailable). Verify UI status and available operations match the scoped graph, including generic rendering for an added type. Record the pilot's integration and memory results before expanding the interface. Covers CORE-1, FLOW-1, UX-1, UX-2, MEAS-1, ATT-1, INT-1, INT-2, PRJ-1, EXEC-1, EXEC-2 and OPS-1 in the pilot scope.

## 2. Generalize workflows, project context and controls

Extend the DAG runner to typed branches, joins, parallel work, configured consultations and recovery. Prove human, instructed model and direct paths. Distinguish operator stop, timeout and revocation. Add provisional projects, overlapping links and a second project backend with versioned writes. Validate a mixed-domain fixture with a human verification step and no repository. Expose lifecycle and evidence through the supported harness, MCP, CLI and manual surfaces.

Expose the canonical settings registry as a configuration skill. Start with inspect, typed preview, conditional apply and scoped rollback. Authorize changes and bundled actions under the pre-change policy. Add optional model-written progress, and prototype the Home activity graph against real assignment events. Retain the accessible list and judge the graph from the operator’s actual use.

**Exit.** One intent can link to two projects without broadening access. A concurrent backend edit is preserved. Gate behavior and recovery survive restart. A bundled gate-removal proposal cannot authorize itself. Progress and evidence agree across supported surfaces. Extends CORE-1–4, FLOW-1, CFG-1, UX-1–2, PRJ-2–3 and ATT-2.

## 3. Validate expertise reuse and outcome measurement

Add versioned expertise entries, scoped activation and revocation, dependency resolution, gap reporting and attempt pins. Carry forward one tested initial-frame preparation from the pilot with its applicability conditions and observed exceptions. Start with manual authoring and one bounded research run. Compare a lower-cost model with and without the authored expertise on held-out cases with independently sourced expected outcomes. Include cases that require escalation. Record cost to author, review and maintain the entry, plus verified outcomes, per-run spend and time.

Add deterministic forecasts from observed runs. Separate time on verified runs from probability of verification by a deadline. Publish assumptions, comparable-run coverage and forecast error. Start allowance calibration with recorded and simulated quota readings, including overlapping windows, concurrent workers, cache mix and changing charging. Keep estimates and enforced limits distinct and admit work across applicable limits atomically.

**Exit.** Reuse requires no authoring-model calls. Revocation stops affected downstream work. A matched report shows cost and time to verified outcome, even if the results show no savings. A forecast can be replayed against its original evidence. The quota fixture shows drift, uncertainty and no double counting, and declines work when a required hard cap cannot be enforced. Covers EXP-1, EXP-3, EST-1, MEAS-1 and allowance-specific CFG-1.

## 4. Add event-driven coordination and unattended service operation

Start with one real event source and a policy for when to investigate, notify or proceed. Add a reference calendar and one external adapter, then pluggable ChatOps and outbound updates. Integrate these into the same Dev Manager workflow. Keep identity verification and intake limits independently configurable. Use staff availability and bookings in estimates with provenance and freshness.

Exercise service restart, stale calendar events, catch-up, duplicate messages, advisory timeout and a required gate. Keep unrelated work running where policy permits. Add one clear return-to-work summary that distinguishes milestones, blocked steps and material decisions.

**Exit.** An open route can start bounded work and a named-approver route can require verification. One rescheduled occurrence triggers the right reevaluation without duplicate effects. Required gates hold through downtime and advisory steps follow their configured fallback. The operator can reconstruct unattended activity and find the underlying evidence. Covers MSG-1, CAL-1, PRO-1–2 and ATT-2.

## 5. Replace workers locally, then add Ozma and remote placement

Prove placement, portable checkpoint recovery, authorized inference fallback and a stable Home activity view with a managed local pool. Classify adapters by point-of-effect fencing. Hold conflicting reassignment where an unfenced effect remains uncertain. Then enroll a second host and verify dispatch, revocation, network partitions and reconciliation with distinct worker identities.

Develop the first-class Ozma inference wire contract in parallel with local worker work. Keep a versioned conformance fixture shared with Ozma. Start with graph-only fulfillment over a scoped view. Add model-backed or hybrid inference after delegated limits and data routing are demonstrated.

**Exit.** A replacement host resumes portable state or restarts from a safe step. A fenced target rejects a stale effect. Two peers complete a graph-only request without model calls. Cancellation, replay after access revocation and refusal of a prohibited fallback all pass. Covers MESH-1–2 and distributed CORE-2–3 and EXEC-2.

## 6. Provision capacity on premises and in the cloud

Implement provision, inspect, drain and release behind a provider adapter. Exercise a managed local or on-prem pool before a disposable cloud run. Confirm which Docker service the credits cover and whether its interface supports the required lifecycle. Set a bounded workload and spending allowance for the pilot. Report credit or billed usage, startup and idle time, plus verified teardown.

**Exit.** An ambiguous create is reconciled without duplicating the resource or releasing its reservation early. Shared capacity returns to its pool and an enrolled external host is left intact. The cloud pilot has a confirmed release receipt and recorded cost or credit usage. Covers CAP-1.

## 7. Share measurements and expand expertise distribution

Stabilize local measurement before enabling opt-in uploads to ozagia.com. Validate outbound payloads, sparse cohort suppression, retention and opt-out end to end. Make aggregate downloads independently configurable. Verify that pooled baselines remain labeled and compare them with local results before using them for estimator or routing decisions.

Add dynamic expertise fetching once package provenance, compatibility, version pins and revocation work locally. Keep activation and access to optional specialist models under deployment policy.

**Exit.** Local workflows and estimates work entirely offline. Opt-out stops new uploads and clears queued data. Published cohorts meet the documented disclosure rules. A fetched expertise version can be evaluated, activated and revoked without changing historical pins. Covers TEL-1 and EXP-2.

## Delivery controls

Stages 2 and 3 can progress in parallel once the core event and evidence contracts are stable. The calendar and messaging adapters can be built independently against the service contract. Cloud provisioning depends on worker reconciliation and budget enforcement. Telemetry depends on stable local measurements, and dynamic expertise distribution depends on local authoring and activation.

For each stage, record the pinned revision, supported capabilities, evidence for each exit criterion and any newly discovered limitation. Use offline fixtures for failures and quota scenarios, then verify provider and harness claims on the actual integration. Live model drivers require the repository's live opt-in and human approval. Treat the Docker credit run as a separate live integration milestone.

Release capabilities independently through the existing settings boundary. Preserve local and manual use at each stage. When disabling an integration, stop new admissions and reconcile in-flight operations. Before any Dev Manager cutover, verify the lifecycle ownership map and preserve a path back to the existing operation. Review this plan after the pilot using observed outcome quality, attention and recovery rather than feature count.
