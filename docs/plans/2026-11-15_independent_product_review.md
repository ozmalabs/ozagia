# Ozagia: product and functionality review

Review date: 2026-11-15. This reviews the working tree, including uncommitted research-mode work. Competitor descriptions come from their own documentation and are not independent performance comparisons. This is a product and architecture review, not an exhaustive security audit.

## Recommendation

Position ozagia as a local, inspectable context and evidence layer for existing agents, with coding and research as separate entry points. Its strongest combination is a repository graph, incremental updates, structured edits and provenance-aware research records. Prioritize proving that those capabilities improve real workflows, keeping results fresh, and making their limitations visible before adding more surface area.

## What exists and what the evidence says

- Coding mode includes file and symbol graphs, lexical/graph search, repo maps, optional LSP and SCIP, graph-addressed edit transactions, MCP, OpenCode capture and agent harnesses. The core has no mandatory dependencies. See [README](../../README.md), [symbol graph](../symbol_graph.md), [LSP](../lsp.md), [SCIP](../scip.md) and [edit transactions](../cst_edit.md). Tree-sitter relationships are heuristic; LSP can be incomplete while a server indexes, and its rename output is a preview. SCIP protobuf support is documented as untested in the recorded environment.
- Research mode already has reference and artifact handling, source locators, search, screening records, review and appraisal structures, citation graphs and theory ledgers. The default hash-bow vector option is a lexical baseline, not a semantic model; PDF math is degraded. Review records and candidate citations are not independently verified conclusions. See [research mode](../research.md).
- The [30-task Ocelot retrieval evaluation](../results/ocelot_retrieval_v2.md) reports content-tier recall of 0.717 for code search versus 0.283 for the repo map at a nominal 500-token budget; grep path recall was 0.700 but its content-tier recall was zero by this instrument's definition. This is one repository, a small labeled set, estimated tokens and unequal output forms, not proof of downstream task gains. The combined arm can consume twice its nominal budget.
- The [seven-task agent pilot](../results/ocelot_agent_pilot_opencode.md) reports 7/7 successes in each arm with one repeat. The graph arm averaged 32,401 input tokens versus 27,504 baseline and required 64.3 seconds preparation versus zero; reported average graph calls were 0.3. These are observations, not statistically reliable effect estimates, and the pilot predates parts of the current integration. It does not establish an advantage.
- Live Claude Code hooks are explicitly untested in the README. The LSP tests described in its docs use fake servers by default; optional live tests can skip. Many newer research files are currently uncommitted and should be considered part of the reviewed working tree rather than a released baseline.

## Alternatives and implications

| Alternative | Relevant capability | Implication for ozagia |
| --- | --- | --- |
| [Serena](https://github.com/oraios/serena) | MCP semantic symbol navigation and editing via LSP, with broad language-server support. | Competing on the number of LSP languages alone is expensive. Offer dependable coverage for chosen languages, clear provenance and composable graph context. |
| [CodeGraphContext](https://github.com/CodeGraphContext/CodeGraphContext) | Local code graph, tree-sitter/SCIP, MCP and file watching. | A graph plus MCP is not a differentiator on its own; freshness, correctness, measured outcomes and low setup friction matter. |
| [Aider](https://aider.chat/docs/) | Agent with a repository map and editing workflow. | Benchmark the whole workflow against strong agent-native context, not merely a path listing. Aider notes maps can overwhelm some models. |
| [Elicit](https://support.elicit.com/en/articles/14759154-systematic-reviews-in-elicit) | Guided literature search, screening, extraction, source quotes and reports; paid tiers. | Research users expect an end-to-end, reviewable workflow and evidence linked at the field level. Ozagia can emphasize local control and exportable provenance. |
| [ASReview](https://asreview.nl/project/intro_paper_asreview/) | Open-source active-learning assisted screening. | Consider interoperability and evaluated screening prioritization rather than building an unvalidated classifier. |

These products have different scopes, installation needs and licensing; feature mentions are vendor claims and do not establish which performs better.

## Ozma-ai / Codeclub ecosystem opportunity

The initial review underweighted the sibling [ozma-ai checkout](../../../ozma-ai/README.md). Ozagia can provide graph and evidence capabilities to a wider Ozma product, alongside its existing model gateway, UI, task runner and operational integrations. This is source inspection, not live validation: a route's existence does not establish end-to-end maturity, and the README's performance and cost claims need independent evaluation. The Rust README describes that implementation as work in progress.

| Existing ozma-ai surface | Potential value | Proposed integration |
| --- | --- | --- |
| [OpenAI-compatible proxy and context pipeline](../../../ozma-ai/README.md), compression, hints and routing | Give existing clients fresh task-specific source spans, relationships and test evidence. | Add an optional context-provider adapter with budgets, provenance, timeouts and a fallback. Evaluate baseline, ozagia alone, ozma-ai alone and both; do not assume their gains add together. |
| [Repo group and contract API](../../../ozma-ai/backend/ozma/repos/api.py) and [contract checker](../../../ozma-ai/backend/ozma/repos/contracts.py) | Trace API operations, schemas, generated clients, consumers and tests across repositories. | Start read-only with OpenAPI operations and explicit consumer mappings. Attach spans, revisions and provenance. A hash difference shows change, not necessarily a breaking change; missing repos or tools must be reported as unknown. |
| [OpenAPI compressor](../../../ozma-ai/research/ozmalib/compress/openapi.py), hints and checks | Present the endpoints and types relevant to a change and link findings to graph nodes. | Reuse optionally after fixture-based validation, with links to original locations and clear unsupported references. Preserve relevant authentication, request/response and versioning details. |
| [Task API](../../../ozma-ai/backend/ozma/devloop/tasks_api.py), CI, lint and security APIs | Provide task context and affected tests; attach results to session history. | Begin with read-only context and result ingestion. Keep execution and external writes in explicitly invoked workflows. The task stream is marked as a placeholder in source. |
| [FastAPI app and routers](../../../ozma-ai/backend/ozma/main.py), web UI and VS Code extension | Offer graph search, status, impact and evidence to existing clients. | Design a versioned, typed, read-only API in an optional integration or ozma-ai router, with discovery, errors and pagination. Keep FastAPI out of ozagia's stdlib core; authorize repository access before network exposure. |

**Priority revision:** move API surface and contract discovery and an Ozma context-provider proof of concept into P1, ahead of general cross-repository graphs and extra languages. Use a multi-service fixture to demonstrate endpoint → schema → consumer → test traceability, freshness after edits and checkout changes, and explicit unknowns. Define the consumer contract first and preserve MCP and CLI behavior. Wider multi-repository operations, mutating HTTP APIs and coordinated actions remain later work.

## Prioritized proposal

### P0: Establish reproducible value and trust

1. **Benchmark agent outcomes.** Extend the existing harness with frozen, held-out tasks across at least three repositories and languages, including multi-file changes and unfamiliar terminology. Compare the same agent/model/configuration with native tools only, ozagia MCP, and automatic capture; add Serena or another external baseline where feasible. Randomize order, repeat paired runs, isolate task setup, and report confidence intervals, failures, tool usage, total tokens, cold and warm setup time, wall time and cost. Define the task set and primary success measure before tuning; keep a separate holdout. Use only a separately approved live run per AGENTS.md. Acceptance: a published, reproducible report with per-task artifacts and no omitted failures; claim gains only if supported by results.
2. **Expose freshness and provenance everywhere.** Add a compact status object to context/search/navigation responses: indexed root and revision, snapshot or content version, refresh time, changed-file/staleness state, source of each relationship (syntax, LSP, SCIP, adapter), confidence where applicable and missing capabilities. Distinguish unknown/incomplete from verified absence. Preserve existing confidence information rather than inventing calibrated probabilities. Acceptance: tests cover edits outside hooks, deletes, renames, checkout changes, missing servers and stale SCIP, and queries never silently claim a stale result is current.
3. **Make adoption observable.** Provide a single doctor/status command for missing extras, active integrations, parser/language coverage, snapshot health, ignore rules and reasons for degraded operation. Measure tool calls and preparation costs locally with opt-in telemetry or exportable session reports. Smoke-test current MCP client protocol and a real Claude Code hook flow when available; clearly label each verified client/version. Acceptance: a new user can diagnose an absent parser, stale index and failed language server without inspecting source.

### P1: Improve the coding workflow

4. **Freshness across all edit paths.** Build on existing reingest and daemon capture with an optional local watcher and a reconciliation fallback at query/session boundaries. Coalesce changes, bound work and handle overflow by marking state uncertain and rebuilding. Do not assume hooks see edits from every client. Acceptance: create/modify/delete/rename, git checkout and changes outside the agent converge to the same graph as a clean rebuild; report lag and benchmark cold/warm/update latency on multiple repository sizes.
5. **Provide one task-context response.** Compose existing search, symbol relationships, relevant tests and recent failures into a budgeted, explainable result; show why each item was selected and source spans. Deduplicate, support progressive expansion and compare it to lexical search and native agent tools at equal *actual* token budgets. Acceptance: held-out content recall and task outcomes improve without a material latency or token regression against the agreed baseline.
6. **Validated multi-file refactoring.** If benchmarks show demand, extend the current preview-first edit transaction to apply supported LSP rename plans as a single reviewed operation, with preflight hashes for every file, path containment, conflict detection, atomicity/rollback and explicit handling of unsupported resource operations. LSP readiness and partial results must be visible. Acceptance: stale inputs, one-file failure, overlapping edits and crash recovery leave no unreported partial change. This is larger than a single-file transaction and should follow a design review.

### P1: Make research evidence auditable

7. **A reproducible review package.** Compose existing screening, extraction, appraisal and manuscript records into a versioned export: protocol and search strings/dates/providers, deduplication and inclusion decisions with reasons, source hashes and passage locators, extraction provenance, unresolved items and a reproducible flow count. Include independent reviewer decisions and reconciliation where recorded; do not manufacture agreement or treat citations as proof. Acceptance: another reviewer can trace each exported conclusion to an accessible artifact and reproduce counts from the package.
8. **Evaluate against labeled literature.** Add a small openly licensed, frozen corpus and human-annotated holdout for retrieval, screening and extraction. Measure recall of included studies, false exclusions, locator validity, extraction field accuracy, missing data and reviewer workload; compare lexical and optional semantic retrieval. Keep model/provider/version and failures in the report. No autonomous exclusion until evidence justifies it. Consider ASReview-compatible exports before implementing active learning.

### P2: Expand only when evidence supports it

9. After the P1 API-contract proof of concept, add language servers or parsers based on actual user repositories and compatibility tests; publish a per-language capability matrix. Consider targeted optional embeddings only if held-out natural-language queries improve enough to justify model size, indexing time and offline operational complexity.
10. Extend explicit API-contract links into general cross-repository graphs and consider a durable database backend after measuring single-snapshot memory, update time and multi-repository use cases. Preserve the zero-dependency core and a migration path. Avoid building a separate full agent UI or proprietary literature corpus before the context and evidence layer demonstrates value.

## Suggested first delivery

Start with P0 items 2 and 3 and the design of item 1. Ship status/provenance and deterministic fixture-based freshness tests first; then run an approved, preregistered live benchmark. In parallel, define the research export schema and a small gold-standard dataset. At the next decision point, use measured failure modes to select task-context improvements or research workflow work. No numeric performance target is asserted before a baseline is measured.
