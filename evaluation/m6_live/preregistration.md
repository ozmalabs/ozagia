# Preregistration: local-Qwen map-arm comparison (M6)

Status: frozen before any live session. No live model call has been made for
this study. The runner, tasks, assertions, schedule and these thresholds are
committed together.

## Question and estimand

Compare two read-only navigation arms on the same 20 Ozagia repository tasks,
with the same local model and the same external tool permissions:

- **baseline** — plain OpenCode, no MCP server, no plugins. Read, grep and glob
  are allowed; the V2 `edit` action (edit/write/patch), `shell`, `webfetch`,
  `websearch` and `external_directory` are denied.
- **maps** — the same permissions plus the Ozagia full MCP server
  (`python -m ozagia.integrations.mcp.server --root <checkout> --mode coding
  --surface full`) against a prebuilt snapshot and a live daemon socket. The
  read-only MCP tools, `dev_maps` and `dev_capabilities` are explicitly
  allowed by their `ozagia_<tool>` permission actions; mutating MCP tools are
  explicitly denied and the default is deny. The server sets `codemode: false`
  so its tools are native tools; `execute`/Code Mode stays denied, keeping
  Code Mode's HTTP `fetch` out of the read-only session.

This estimates the effect of adding the map/self-graph surface to a plain
OpenCode session on this task class. It does not estimate general model
capability, and it does not compare the prompted/context arm or the existing
Ozagia graph-intent path.

## Execution gates

Live mode refuses before the first model session unless all of these hold:

1. Both `--live` and `OZAGIA_EVAL_LIVE=1` are present.
2. Free disk is at least 3 GiB.
3. The source checkout is clean; the pinned commit equals `HEAD`; the
   committed task/assertion/schedule hashes match.
4. The local endpoint serves `qwen3.8-27b` at the fixed loopback URL.
5. The pinned interpreter imports Ozagia from the pinned source tree.
6. The MCP server's static tool table contains `dev_maps`,
   `dev_capabilities`, every allowed read tool and every denied mutating tool.
7. The output directory is outside the source checkout and has no prior
   `runs.jsonl`.

Each session gets a fresh disposable Git clone at the pinned commit, an
isolated `HOME`/XDG/cache/state/temp tree, an allowlisted environment, a
generated OpenCode config with no global plugins or MCP servers, and a
short-lived per-run config that references the local API key through
`{env:M6_API_KEY}`. The value is supplied only in that session's child
environment; the config is deleted after the session and artifacts contain only
a redacted config hash. One session runs at a time.

The maps checkout is prepared outside the timed driver: the snapshot is built,
its freshness is checked, and the daemon is started and ready before the
session. The baseline checkout has no `.ozagia` state. The graph is not
refreshed during a session. Setup time is recorded separately and included in
the setup-inclusive total.

## Primary outcome

**Maps task success is non-inferior to baseline.**

A task counts as verified only when the session completed without timeout,
driver or treatment error, and the held-out deterministic scorer reports every
required group matched and no forbidden phrase. The primary comparison is the
number of verified successes per arm over the same 20 tasks, with every
invalid, failed, unknown and unpaired result reported. No substitution or
silent rerun is allowed. A one-repeat, 20-task result is a descriptive paired
comparison, not a general capability claim.

## Secondary outcome

**Maps median setup-inclusive time-to-verified-outcome is at least 10% lower
than baseline across the 20 paired tasks.**

- Time-to-verified-outcome is `setup_s + driver_wall_s` for a verified
  session: disposable checkout, snapshot build and daemon readiness for maps;
  checkout only for baseline; then the OpenCode session.
- The statistic is the median of the per-task setup-inclusive times over pairs
  where **both** arms verified.
- `10% lower` means `(baseline_median - maps_median) / baseline_median >= 0.10`.
- Pairs where either arm failed, timed out, was invalid or has unknown time are
  reported in `pairs_not_both_verified` and excluded only from the secondary
  median. They are never dropped from the report.
- Fewer than 10 both-verified pairs is reported as insufficient evidence, not
  as a pass.

## Reported measures

For every session: task, arm, pair/order, status, timeout, exit code, final
answer (bounded), deterministic score, required/failed assertion ids,
forbidden hits, setup and driver wall times, setup-inclusive time, input,
output and cache-read/cache-write tokens where reported, cost where reported,
tool names/counts, MCP and `dev_maps`/`dev_capabilities` call counts, permission
denials, bounded errors, source commit/tree, config-redacted hash and snapshot
freshness. Aggregates report totals and medians per arm; unknown token values
are counted as unknown, not as zero.

The analysis is arm-blinded only in the sense that scoring is a deterministic
string check applied to captured answers; the scorer does not call a model.
Per-task rows are reported for both arms, including failed and unpaired cells.

## Decision rule

- Primary passes only if maps verified successes are at least baseline verified
  successes and the invalid/failed cells are reported.
- Secondary passes only if at least 10 pairs have both arms verified, the maps
  median is at least 10% lower, and the failed/unknown pairs are listed.
- If the primary passes but the secondary does not, report non-inferior success
  without a speed claim.
- If the maps arm is worse, or a validity gate fails, report that result without
  reclassifying it as a harness success.

No threshold is changed after seeing output. A source or corpus change requires
a new version and a new preregistration before any live session.

## Separation from other evidence

The prompted/context arm and the existing-Ozagia 72-session study are separate
evidence. They are not pooled with these 40 sessions, not used to fill missing
cells, and not described as replications of this study. This study also does
not test cold versus warm indexes, a larger or smaller model, multiple
repeats, other repositories, or a model-judge score.
